# Adding Algorithms to ArduSim2

This guide covers everything you need to know to integrate a new algorithm into the system properly — from the directory layout to the schema contract the GUI depends on. There are no restrictions on language or technology, so feel free to use whatever stack makes sense for your use case.

---

## Directory structure

Each algorithm lives as its own self-contained project under:

```
src/algorithms/<your-algorithm-name>/
```

Two files are **mandatory** regardless of the language or framework you use:

| File          | Purpose                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------- |
| `Dockerfile`  | Builds and runs the algorithm as a containerized service                                          |
| `schema.json` | Describes the algorithm's configuration so the GUI can render a form and generate a `config.json` |

Everything else (source code, dependencies, tests, etc.) is up to you.

```
src/algorithms/my-algorithm/
├── Dockerfile          ← required
├── schema.json         ← required
├── README.md           ← required (see below)
├── src/
│   └── ...
└── ...
```

## The README

Every algorithm must ship with a `README.md` inside its own directory. The goal is that any developer looking at the algorithm for the first time can understand what it does, how it works, and how to run it — without having to read the source code.

At minimum, cover:

- **What the algorithm does** and the problem it solves.
- **How it works** at a high level — the main logic, states, or phases involved.
- **Inputs and outputs** — what messages or topics it consumes and produces, and in what format.
- **Configuration** — a brief description of the most important parameters from `schema.json`. You don't need to duplicate every field, but call out anything non-obvious.
- **Known limitations or assumptions** — anything a future developer should be aware of before modifying it.

### Linking from the root README

Once your algorithm is ready, add an entry for it in the **Implemented Algorithms** section of the [root README](../README.md). Use a simple table row with the algorithm name (linked to its own README) and a short one-line description:

```markdown
## Implemented Algorithms

| Algorithm                                             | Description                                                                |
| ----------------------------------------------------- | -------------------------------------------------------------------------- |
| [Mission](src/algorithms/mission/README.md)           | Follows a predefined KML route, sending suggestions to the UAV controller. |
| [Follow Me](src/algorithms/follow_me/README.md)       | Master/slave swarm behaviour where slaves follows a master UAV.            |
| [My Algorithm](src/algorithms/my-algorithm/README.md) | One-line description of what it does.                                      |
```

Keep the description short — one sentence is enough. The full explanation lives in the algorithm's own README.

## The Dockerfile

The Dockerfile is used to build and deploy the algorithm container. The entrypoint **must** expect a `config.json` file as input — that file is generated by the GUI from the schema and injected into the container at runtime.

A minimal example using Go:

```dockerfile
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o main ./cmd/main.go

FROM alpine:latest
WORKDIR /app
COPY --from=builder /app/main .

ENTRYPOINT ["./main", "config.json"]
```

The same pattern applies regardless of language. A Python example:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

ENTRYPOINT ["python", "main.py", "config.json"]
```

The only invariant is that the entrypoint receives `config.json` as its first argument. Everything else is your call.

### Environment variables injected by the GUI

The GUI automatically injects the following environment variables into every container it starts, regardless of what the algorithm does:

| Variable   | Value                            | Description                                                                                                                                                 |
| ---------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `UAV_ID`   | Numeric ID of the UAV instance   | Identifies which UAV this container belongs to. Use it to tag log messages, derive per-UAV topic names, or implement any other instance-specific behaviour. |
| `SWARM_ID` | Numeric ID of the Swarm instance | Identifies which Swarm the UAV belongs to. Use it to tag log messages, derive per-swarm topic name, or implement any other instance-specific behabiour.     |

You don't need to declare these in your `schema.json` — they are always present. If you run the container manually (e.g. for local testing), you'll need to set them yourself:

```bash
UAV_ID=1 ./main config.json
```

## The schema.json

The `schema.json` file is what ties your algorithm into the system. The GUI reads this file to render a configuration form and uses it to produce the `config.json` that gets passed to your container.

### Required top-level fields

| Field        | Description                                                                                                                                                                        |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `service_id` | A unique identifier for this algorithm. Other services will use this ID to reference yours (e.g. when routing messages). Keep it short and lowercase — `mission`, `followme`, etc. |
| `title`      | Human-readable name shown in the GUI.                                                                                                                                              |
| `properties` | Object containing all configuration parameters.                                                                                                                                    |

```json
{
  "service_id": "my-algorithm",
  "title": "My Algorithm",
  "properties": {
    ...
  }
}
```

> **Important:** `service_id` is the canonical identifier for your service within the platform. Any other service that needs to talk to yours will reference this exact string. Pick a name and don't change it once the algorithm is integrated.

### Defining properties

Each key inside `properties` maps directly to a field in the generated `config.json`. Here are the rules:

- Every property **should** have a `default` value unless the field genuinely requires user input (like a mission file path). Properties without a default will be left empty unless the user fills them in.
- To make a property appear in the GUI form, it **must** have both a `title` and a `type` field.
- Properties that are internal or have sensible fixed defaults (like broker IPs and topics) can omit `title` and `type` — they'll be written to `config.json` with their default values without appearing in the form.

#### Supported types and formats

**Scalar values:**

```json
"my_timeout": {
  "type": "number",
  "title": "Timeout (s)",
  "default": 5.0
}
```

```json
"enabled": {
  "type": "boolean",
  "title": "Enable Feature",
  "default": true
}
```

**String with predefined options (enum):**

```json
"mission_end": {
  "type": "string",
  "title": "Mission End Behaviour",
  "enum": ["unmodified", "land", "rtl"],
  "default": "unmodified"
}
```

**File upload (the GUI renders a file picker):**

```json
"mission_file": {
  "type": "string",
  "format": "kml",
  "contentMediaType": "application/vnd.google-earth.kml+xml",
  "title": "Mission Route (.kml)"
}
```

Note that file fields typically have no `default` since the user must provide the file explicitly. Anyways, you can specify it.

### Networking properties

Your schema should include all IPs, ports, and message topics your algorithm uses. This makes deployments explicit and lets the GUI expose overrides when needed.

Networking properties generally have fixed defaults and don't need to appear in the GUI form, so you can omit `title` and `type`:

```json
"broker_ip": {
  "default": "communication_module"
},
"broker_port": {
  "default": 3400
},
"telemetry_topic": {
  "default": "uav/telemetry"
},
"suggestions_topic": {
  "default": "uav/suggestions"
},
"subscription_topic": {
  "default": "algo/my-algorithm"
},
"logs_topic": {
  "default": "uav/logs"
}
```

The `broker_ip` default (`"communication_module"`) resolves via Docker networking to the communication module container. Don't hardcode actual IP addresses there.

The `mission` algorithm schema is a good reference. Here's an annotated version of a similar schema for a hypothetical algorithm:

```json
{

    "route_file": {
```

## Logging

Algorithms should publish their log messages to the logger service via the broker, using the topic declared in `logs_topic` (typically `uav/logs`). This is how the platform aggregates logs from all running containers in one place, making it much easier to debug a running simulation without having to inspect each container individually.

The expected message format on that topic is whatever the logger service consumes — check the [logger README](../src/logger/README.md) for the exact structure, but in general it should include at least a severity level, a timestamp, and the message text.

Beyond publishing to the broker, **also print the same messages to stdout/stderr** in your container. This serves as a fallback: if the broker isn't reachable yet (which can happen early in startup, see the section below), the logs are still visible via `docker logs` or however the orchestrator surfaces container output. It's also just handy during local development.

In short: send logs to the broker for the platform, and print them to the console for yourself.

## Handling connectivity in cloud simulations

When the simulation runs in a cloud environment, container startup is not perfectly synchronised. Your algorithm may start sending messages or attempting connections before the communication module is ready, resulting in dropped messages or refused connections — especially during the first few seconds.

**Don't assume the network is ready on startup.** Design your algorithm to cope with this:

- **Retry connection establishment.** If you're connecting to a broker or any other service, wrap the initial connection in a retry loop with a short delay (e.g. exponential backoff starting at 500ms, capped at ~10s).
- **Retry the first critical messages.** If your algorithm sends a message that kicks off the behaviour (e.g. a start command or initial telemetry subscription), don't fire-and-forget it. Wait for an acknowledgement or resend it until you get one.
- **Log connection failures clearly.** Make noise when a connection attempt fails. It's much easier to debug startup issues if the logs show exactly which endpoint couldn't be reached and how many retries were attempted.
- **Don't crash on connection failure.** Fail gracefully — keep retrying in the background rather than exiting the process. The orchestrator may restart the container, but a retry loop is cleaner and faster.

## Checklist

Before submitting a new algorithm, go through this list:

- [ ] The algorithm lives under `src/algorithms/<name>/`
- [ ] A `Dockerfile` is present and the entrypoint accepts `config.json`
- [ ] A `schema.json` is present with `service_id`, `title`, and `properties`
- [ ] `service_id` is unique across all algorithms in the repository
- [ ] All GUI-visible properties have `title` and `type`
- [ ] All properties that don't require user input have a `default`
- [ ] Networking parameters (IPs, ports, topics) are declared in `properties`
- [ ] The algorithm handles connection failures gracefully at startup
- [ ] Log messages are published to the broker on `logs_topic` and also printed to stdout
- [ ] A `README.md` is present covering what the algorithm does, how it works, and its inputs/outputs
- [ ] The root README's **Implemented Algorithms** table has been updated with a link to the new README
